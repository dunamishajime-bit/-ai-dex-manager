# Loss-Only Entry Firewall Protocol — 2026-08-16

## Purpose

After the current Premium/Basis research line is completed and frozen, the next research program will aggregate historical losing entries from V96 onward and derive entry exclusions **only from recurring loser-side conditions**.

This program must not use winning-entry patterns, best-trade patterns, or hindsight winner clusters to construct the new entry logic.

## Core idea

The research question is inverted:

> Instead of asking "what did winning entries look like?", ask "what causal conditions repeatedly existed before losing entries?" and prohibit new entries when those recurring loss conditions are present.

The resulting architecture is a **generic opportunity trigger + Loss Firewall**.

- The generic opportunity trigger must be simple, common across symbols, and predeclared without fitting to winning trades.
- The Loss Firewall is learned only from losing historical entries.
- A trade may fire only when the generic opportunity trigger is active AND no validated loss condition is present.

This is not allowed to become "enter whenever none of the old loss conditions are true" because that would create uncontrolled firing and a hidden optimization problem.

## Source population

Collect all available trade/entry records from research versions V96 onward, including failed candidates, across:

- ETH
- BNB
- SOL
- LINK
- AVAX
- BTC only when it was actually a tradable research candidate; otherwise BTC remains reference context

Use every available period already generated by those historical research runs. Preserve the original run/version, symbol, side, entry timestamp, exit timestamp, costs, delay/stress mode, PnL, MFE, MAE, exit reason, and any causal feature snapshot that was available at entry time.

Do not reconstruct missing features with future information.

## Loser definition

Primary loser label:

- net trade return < 0 after that run's declared execution cost assumptions.

Secondary severity labels:

- SMALL_LOSS
- MATERIAL_LOSS
- LARGE_LOSS
- IMMEDIATE_ADVERSE
- GIVEBACK_AFTER_MFE
- COST_FLIP
- LATENCY_FLIP

Severity boundaries must be fixed before aggregate results are inspected. They may be defined by distribution-free rules such as sign, MFE/MAE ordering, and whether Normal vs Stress flips sign; do not optimize numeric cutoffs to improve final strategy return.

## Allowed explanatory features

Only information causally available at or before entry may be used, for example:

- multi-horizon returns / normalized returns
- volatility state and volatility change
- efficiency / path quality
- range position / compression / expansion
- cross-sectional breadth
- relative strength / residual return
- BTC or common-market-factor context
- long/short side
- time since prior regime/ownership change
- funding, premium/basis, OI, taker flow, or long-short positioning only when the historical source existed and the timestamp alignment is causal
- liquidity/execution context when historically available

Forbidden:

- future return
- future MFE/MAE as an entry feature
- future exit reason
- winner-derived feature selection
- best-trade contribution
- manually selecting features because they improve historical winners

## Loss-pattern acceptance rule

A loss condition can enter the Firewall only if it is **recurrent and cross-context**, not a one-period artifact.

At minimum it must satisfy all of the following:

1. appear in multiple independent research versions or architecture families;
2. recur in at least two non-overlapping calendar periods;
3. not depend on one symbol only unless explicitly declared a symbol-specific structural defect;
4. materially increase loss probability or loss severity relative to the unconditional entry population;
5. remain directionally harmful under Stress execution where the source run supports Stress replay;
6. have a causal interpretation that can be stated before seeing the next test period;
7. not be a near-duplicate of another accepted loss condition.

No continuous threshold optimization is permitted. Prefer categorical states, sign agreement/disagreement, quantile buckets fixed before evaluation, or standard z-score bands defined once globally.

## Anti-overfit controls

### 1. Version holdout

Do not derive all loss conditions from every version simultaneously.

Partition historical versions into:

- LOSS-DISCOVERY versions
- LOSS-VALIDATION versions

A loss condition must be discovered in one set and independently recur in the other before it may enter the Firewall.

### 2. Time holdout

Within each version family, maintain non-overlapping time partitions. A condition seen only in one year is not a universal blocker.

### 3. Symbol transfer

Prefer loss conditions that transfer across multiple symbols. Symbol-specific blockers require stronger evidence and must not become symbol-specific threshold grids.

### 4. One-way information flow

Winning trades may be used only after the Firewall is frozen to measure collateral damage, never to design or select the blocker itself.

This means the order is:

1. derive blockers from losers only;
2. freeze blocker definitions and source hash;
3. then evaluate how many winning opportunities were also excluded;
4. do not modify the blocker to recover excluded winners in the same evidence set.

### 5. No rescue tuning

If a frozen Loss Firewall removes too many trades or fails return goals, do not relax/tighten its thresholds using the same data. Diagnose and close that candidate.

## Required diagnostic outputs

Produce machine-readable trade-level and aggregate artifacts containing:

- version / run / SHA / symbol / side
- entry timestamp and exit timestamp
- Normal/Stress PnL where available
- MFE / MAE where available
- causal feature snapshot at entry
- loser severity classification
- assigned loss-pattern IDs
- number of recurring versions
- number of recurring years
- number of recurring symbols
- effect size versus unconditional entries
- Stress consistency
- exclusion count

Also produce a Markdown report with a ranked list of accepted and rejected loss patterns and the reason each was accepted/rejected.

## Candidate architecture after the Firewall is frozen

The first candidate must use:

1. a simple predeclared generic opportunity activation that is not learned from winners;
2. the frozen Loss Firewall;
3. fixed lifecycle rules that are not optimized from winning trades;
4. the existing annual return standard.

The first candidate may not add positive winner-pattern rules after seeing results.

## Return standard

80% annual return is a failure floor, not the target.

- every 1Y return >= 80%
- median 1Y return >= 100%
- 3Y CAGR >= 100%
- strong candidate: every 1Y >= 100% and 3Y CAGR >= 120%
- PF, PF-without-best, DD, Stress, concentration, sample size, and execution-cost robustness remain mandatory

No leverage/gross increase may be used to manufacture compliance.

## Sequencing

1. Complete and freeze the currently active Premium/Basis research protocol.
2. Inventory all V96+ historical research artifacts and trade-level entry records.
3. Build a normalized loss-event dataset without strategy modification.
4. Freeze LOSS-DISCOVERY / LOSS-VALIDATION partitions before extracting patterns.
5. Derive recurring loss conditions from losers only.
6. Freeze the Loss Firewall.
7. Only after freeze, measure excluded winners and candidate portfolio results.
8. If it fails, do not tune the Firewall against the same evidence; require genuinely new evidence or a different research premise.
